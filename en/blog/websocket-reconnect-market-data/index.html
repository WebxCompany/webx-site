Realtime market data: surviving a WebSocket disconnect

19 November 20266 min readWEBX GROUP

The failure that does not look like a failure

Almost every WebSocket library has a reconnect: true flag, and it makes disconnects feel solved: the socket returns, events flow again. In practice a terminal after reconnect sits in one of three states, and all three look healthy from the outside: the book was rebuilt from deltas applied to a stale snapshot; deltas were lost during the gap and the book silently drifts; events arrived twice and a candle's volume is doubled.

The connection is alive, the “connected clients” dashboard is green, and the data is wrong. That is the worst incident class in a terminal: not an outage, but a silent divergence a trader notices before your monitoring does.

A TCP reset is not an anomaly. Networks change, load balancers recycle, exchanges rotate endpoints. Recovery belongs in your protocol, not in a client setting.

Four kinds of loss

Four classes, four different mechanisms:

  • Missing events. The socket dropped mid-feed; everything from 200 ms to 30 seconds is gone unless the client can backfill.
  • Broken ordering. Live events and REST backfill interleave; for a book, set(100.5) then volume +1 is not the reverse sequence.
  • Duplicates. A reconnect re-subscribes, and the first packet is a snapshot landing on already-applied deltas.
  • Lost client state. Subscriptions, open instruments and accumulated book state are gone, so the user stares at an empty chart.

Without an explicit answer to all four, data will be lost — the question is only how often.

The recovery protocol

Rule one: a sequence number, and gap detection

Every instrument needs a monotonic counter: an exchange-provided sequence/updateId, or an offset stamped by your own ingest layer. The client keeps the last applied offset and compares it to the first offset of the new stream: equal to last + 1 means contiguous; greater means a gap, so backfill (last, new) from history and apply in order; less than or equal to last is a duplicate or a replay, drop it.

on event(e):
    if e.offset == lastApplied + 1: apply(e); lastApplied = e.offset
    elif e.offset > lastApplied + 1: gap(lastApplied, e.offset)
    else: drop(e)

A dozen lines remove a whole class of silent divergence. Without them, “data is flowing” checks stay green while the numbers are wrong.

Rule two: snapshot and delta without the race

The book lives in two modes: an initial snapshot and a delta stream, and the classic bug is the ordering between them.

  1. Snapshot-first with a buffer. Subscribe to deltas, buffer them, request the snapshot, then apply only buffered deltas above the snapshot offset.
  2. Offset backfill on reconnect. Take the first offset of the new stream, pull the missing range from history, apply in order, then switch to live.
  3. Full snapshot for long gaps. If the gap exceeds the backfill window, a fresh snapshot beats replaying minutes of deltas.

If the source ships an offset with the snapshot, use it as the buffer cut-off; if not, stamp the snapshot at ingest — otherwise the GET/WebSocket race never closes.

Rule three: ordering and idempotency

Partition by instrument so deltas for one book cannot overtake each other in parallel processing. Make apply idempotent: discard a delta whose offset was already applied. Deduplication by offset survives reconnects and backfill replays; deduplication by “timestamp plus price” does not, because two distinct trades can share both.

Rule four: backpressure

At market open update rates multiply and slow clients queue up. Our starting configuration (defaults to tune per project, not an SLA): batch updates over a 50–100 ms window; heartbeat every 15–30 seconds with zombie connections closed on timeout; a per-client queue limit (order of a thousand messages) after which the client is disconnected rather than allowed to slow everyone down; subscribe only to what is on screen.

Rule five: degradation must be visible

The most expensive incident is not a crash — it is data stopping while the connection stays up. Minimum: age of the last event per instrument with an alert, detected gaps and backfills, reconnects and their duration, queue depth, source-to-gateway latency. “Candles received” is not a substitute: it can look stable while one instrument is silently dead.

Acceptance checklist

  1. Every event carries a monotonic, unique offset.
  2. A 30-second disconnect leaves no holes in the book.
  3. A gap longer than the backfill window triggers a full snapshot, not a guess.
  4. A re-delivered event does not change state.
  5. Delta order for one instrument survives parallel processing.
  6. A slow client is disconnected by limit without degrading others.
  7. Degradation is visible in the UI: a stale book does not look alive.
  8. A load test exercises recovery under load, not on a quiet market.

A failed item is not “technical debt for later” — it is a known incident class that surfaces at the first volatility spike.

Where to go next

Build the protocol once: offsets, gap detection, snapshot and delta without a race, idempotent apply, backpressure, and a “when did data last arrive” metric.

FAQ

Is a library's automatic reconnect enough?

No. Reconnect restores the socket, not the state: the library does not know which events were missed, in what order to apply a buffer, or where the snapshot boundary sits. That is your protocol.

How much data is lost on a disconnect?

It depends on gap length and event rate: 30 seconds on an active instrument means hundreds of book updates. Restore from the source's history endpoint and apply by offset; if the gap exceeds the history window, a fresh snapshot is cheaper.

How do we test reconnect behaviour before production?

Force disconnects at varying intervals in staging, run a load test that drops a share of connections mid-flight, and verify recovery with a deliberately slow consumer. Add a re-delivery test: send the same event twice and assert the state is unchanged.
