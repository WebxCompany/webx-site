How we build a realtime terminal: market-data architecture

12 November 20266 min readWEBX GROUP

From the outside a trading terminal looks simple: a chart, an order book, an instrument list, a buy button. Inside it is a data pipeline that never stops and fails quietly. A candle goes missing, the order book shows a five-second-old price, history and realtime disagree — and the person who notices is not monitoring but a trader.

Below is the architecture we use in N9 and on client projects. It is not the only right approach, but it answers concrete questions: where to keep history, how not to lose events on reconnect, and why the frontend should not know which exchange a candle came from.

Three contours that must not be mixed

The first mistake of almost any MVP is a single process that connects to an exchange, writes to a database and pushes to the browser. With one source it works. Then a second source and a third time zone appear, and the system turns into a pile of if-statements. We separate three contours:

  • ingest — receive source data, normalise it and lose nothing on a disconnect;
  • query — serve history for a range: candles, trades, volumes;
  • push — deliver updates to all active clients with minimal latency.

Each contour has its own requirements. Ingest tolerates hundreds of milliseconds but not data loss. Query loads storage with heavy aggregations. Push must be fast and scale cheaply with the number of connections. Solving all three in one service means that optimising one breaks another.

Layer 1. Connectors: snapshot plus delta

Every source has its own protocol and habits. One WebSocket streams trades and expects you to assemble candles. Another offers paginated history but no realtime. A third sends a full order-book snapshot and then only changes. A connector owns exactly three things: connect, get the initial state, apply deltas and recover after a disconnect. Everything else is not its job.

Resampling deserves separate attention. Storing candles for every selectable timeframe is pointless: the volume grows as instruments × timeframes × retention. Store a base interval and build aggregates next to the data or at query time — with the same time-rounding rule for every source.

Layer 2. The bus as buffer and event log

Between connectors and consumers we put a bus — Redpanda with the Kafka API in our case. It does three jobs: absorbs spikes (at market open the stream multiplies), enables replay (a new service can read from the start of a partition instead of waiting a day), and decouples consumers so history and realtime read the same stream independently.

The partitioning key matters. With an instrument key, all events for one ticker stay in one partition and keep their order — critical for the order book, where the order of applied deltas changes the resulting price.

Layer 3. History in ClickHouse

Market-data history is about range queries: “all BTC/USDT candles for a month at five-minute steps”. A column store like ClickHouse answers that far faster than a classic relational database when the schema matches the query: sort by instrument and time, partition by date, materialised views for timeframes. PostgreSQL does not disappear — transactions, users, settings and permissions live there. Each store has its job.

Layer 4. The realtime gateway

Client connections are the most expensive part of the system. At hundreds of WebSockets problems appear that are invisible at ten: slow consumers, zombie connections without heartbeat, different network speeds.

  • Per-instrument subscriptions: a client receives only what is on its screen, not the whole market.
  • Batching: updates over 50–100 ms are merged into one message — the network and JSON parser do not pay per tick.
  • Heartbeat and timeouts: an unresponsive connection is closed, not left hanging for a week.
  • Backpressure: a client with an overflowing queue is disconnected by limit instead of slowing everyone else down.

A Go gateway is convenient because thousands of goroutines are cheap and behaviour under load is predictable. The language is not the point: explicit limits and per-connection metrics are.

Layer 5. Frontend: canvas and data outside React

A financial chart is a rendering pipeline more than a UI. Calling setState on every tick and re-rendering hundreds of candles through the virtual DOM drops frames exactly when the market is active. So the chart renders on canvas and the stream flows through subscriptions and mutable structures, bypassing React state. React stays for the interface around it: panels, dialogs, settings, layouts.

Observability: the main incident is “data stopped”

The most frequent and expensive failure in a terminal is not a server crash but a silent data stop: the exchange connection is alive, the process runs, candles do not update. Metrics must answer “when did this instrument last receive an event” and surface degradation in the interface, not only on an engineer's dashboard.

The mandatory minimum: source-to-gateway latency, active subscriptions, queue sizes, backpressure disconnects, age of the last event per instrument. Without them you will learn about the problem from a trader — the worst possible way.

What we would do differently

Starting again, we would fix the event contract sooner: one format, versioning, identical time rounding. Until the contract is fixed, every connector accumulates exceptions and the frontend accumulates “if the source is X” branches. Another lesson: load-test before the first clients, when the load profile can be learned on synthetics rather than in production.
